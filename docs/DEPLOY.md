# Getting Ballast live, and keeping it that way

The goal is **push code → it deploys itself**. Cloudflare does this natively
with **Workers Builds**: connect the GitHub repo once, and every push to the
chosen branch builds and deploys with no terminal ever again.

Everything below was verified against the live Cloudflare account and the
current Cloudflare docs, not recalled. Where something could not be confirmed,
it says so rather than guessing.

---

## The split

**The owner does exactly one thing: authorize Cloudflare to read GitHub.** That
is an OAuth grant between two companies and no API can do it on their behalf.

**Claude does the rest** — the code fixes, the database schema, the first user
account — using the Cloudflare and GitHub connectors. None of it needs a
terminal, `wrangler login`, or GitHub Desktop.

You do **not** need Plaid for any of this. The app deploys and runs without it;
Plaid only matters when you want it reading real bank balances.

## Before the first deploy — Claude's half

Each of these is confirmed, with the evidence that confirmed it.

### 1. `APP_ORIGIN` is still the localhost value

`wrangler.jsonc` line 87 reads `"APP_ORIGIN": "http://localhost:8787"`.

`isLocalDev(env)` is defined as _"APP_ORIGIN starts with `http://`"_, and it
decides whether the session cookie carries `Secure` and which origin the CSRF
check accepts. Deployed unchanged, the Worker would hand out session cookies
with **no Secure flag over the public internet** and reject every write from its
own site as cross-origin. Broken and insecure at once.

`scripts/check-deploy-config.mjs` refuses this — which is why the deploy command
must be `npm run deploy` (see step 4), not the default that skips the guard.

**Chicken-and-egg:** the final URL is unknown until the Worker exists. Deploy
once to learn the `workers.dev` URL, then set `APP_ORIGIN` to it and push. The
first deploy is expected to be unusable; the second is the real one.

### 2. Plain vars belong in the file, secrets belong in the dashboard

Confirmed, and easy to get backwards:

- **Secrets** set in the dashboard **survive** automated deploys. Wrangler never
  deletes them.
- **Plain vars** set in the dashboard are **wiped and re-set from
  `wrangler.jsonc`** on every deploy.

So `APP_ORIGIN` and `PLAID_ENV` must be fixed in the file — editing them in the
dashboard silently reverts on the next push. The three secrets must only ever be
in the dashboard.

### 3. The remote database is empty

`ballast-db` exists but contains only Cloudflare's internal `_cf_KV` table. No
migration has ever been applied remotely, and **a Git deploy does not apply
them** — Workers Builds runs a build command and a deploy command, and
`wrangler deploy` never touches migrations.

Claude applies `0001`, `0002` and `0003` directly through the Cloudflare D1
connector, then writes the three filenames into `d1_migrations` so wrangler
knows they are done. Verified: the connector reaches this exact database and
executes DDL.

Do **not** put `wrangler d1 migrations apply --remote` in the deploy command
unless the Workers Builds API token has been given `D1: Edit` — the token it
generates by default does not have it.

### 4. The deploy command must not be the default

`dist/` is gitignored, so a Git-triggered deploy has nothing to serve unless the
build runs. And the default `npx wrangler deploy` bypasses the predeploy guard
entirely.

Set **Deploy command** to `npm run deploy` (which is `npm run build && wrangler
deploy`, with the guard on `predeploy`). This fixes both problems at once.

### 5. Queues

`wrangler.jsonc` declares a producer, a consumer and a dead-letter queue
(`ballast-sync`, `ballast-sync-dlq`). **A deploy does not create queues** — it
fails if they are missing.

Their existence **could not be confirmed**: no queue-listing tool was available
and the sandbox has no Cloudflare credentials. This is the single most likely
cause of a first build failing.

The simplest fix is to **remove the queue bindings for the first deploy**. The
sync loop they feed is unreachable without Plaid anyway, so nothing is lost, and
it removes the whole class of failure. Put them back with Plaid.

### 6. There is no first user

Even a perfect deploy has no account to log into. Claude inserts the first
`users` row through the D1 connector, with a password hash generated by the
repo's own `hashPassword`.

## The owner's half — one click

Do this only **after** Claude has pushed the fixes above.

1. **Cloudflare dashboard → Workers & Pages → Create application → "Import a
   repository"**.
   Use _Import a repository_ rather than connecting an existing Worker: it
   creates a new Worker from the config, named `ballast` to match
   `wrangler.jsonc`. A name mismatch hard-fails Workers Builds. (The account's
   existing `ballast-finance-app` is unrelated — do not connect to it.)

2. GitHub will ask you to install the app called **"Cloudflare Workers and
   Pages"**. Approve it for `Ballast-Budget-App`. **This is the one click.**

3. On the build settings form:
   - **Production branch:** `claude/phase-0-build-foundation-9hxw0l`
     (it is the repo's only branch and its default; `main` is not required)
   - **Build command:** `npm run build`
   - **Deploy command:** `npm run deploy` ← not the default
   - **Build variables:** leave completely empty. Secrets do not go here.

4. **Save and Deploy**, then watch the build log.

5. Once the Worker exists: **Settings → Variables and Secrets → Add**, type
   **Secret** (not Text), three times:
   `PLAID_CLIENT_ID`, `PLAID_SECRET`, `FIELD_ENCRYPTION_KEY`.

   Generate `FIELD_ENCRYPTION_KEY` fresh with `npm run gen:key` — **never reuse
   the `.dev.vars` value**, and store it in a password manager. Rotating it later
   makes every stored Plaid token permanently undecryptable, recoverable only by
   re-linking every institution by hand.

   Do **not** add `APP_ORIGIN` or `PLAID_ENV` here.

After this, every push to that branch deploys automatically. That is the whole
point of the setup.

## Checking it actually worked

A green build is not a working app — that is the lesson this repo was built on.

1. Open the `workers.dev` URL on a phone, or a phone-width window.
2. **Is the Now-Bar visible without scrolling?** It was not, in every build, for
   the life of Phase 0 and Slice 1.
3. Check both themes — switch the phone between light and dark.
4. Confirm the hero figure is a real number, not an em dash and not `$0`.
5. `/api/health` should return `{"ok":true,...}`.

## Known gaps in this runbook

- Whether `ballast-sync` and `ballast-sync-dlq` exist, and whether the account's
  plan includes Queues. Unverified — no listing tool, no credentials.
- Whether the default Workers Builds token has Queues permission. Reported as
  _likely not_; if a build fails on a permissions error, add `Queues: Edit` and
  `D1: Edit` to the token under **My Profile → API Tokens**.
- Migrations `0001` and `0002` open with `PRAGMA foreign_keys = ON`, which D1
  does not document as supported in the console. If a paste is rejected on that
  line, delete it and re-run — D1 enforces foreign keys by default.
